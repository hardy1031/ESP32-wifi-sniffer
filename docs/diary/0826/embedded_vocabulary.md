## MPU (Microprocessor Unit) と MCU (Microcontroller Unit)

- **MPU**: CPUコア単体のチップ。RAM/ストレージ(Flash)/周辺回路は全部別チップとして外付けが必要。例: Raspberry PiのSoC(Broadcom)
- **MCU**: CPU + RAM + Flash + 周辺回路(UART等)が1チップに統合されたパッケージ。例: ESP32, Arduino
- 使い分けの理由(トレードオフ):
  - MCU: 小さい・安い・低消費電力、ただしRAM/Flash容量はチップ設計時に固定(数百KB〜数MB)
  - MPU: RAM/ストレージを自由に増設可能、フルLinuxのような重いOSを動かせる、ただし高価・複雑・消費電力大
  - → 単純な処理をするセンサー等はMCU、カメラ映像処理のようにメモリと処理能力が要る用途はMPUが向く

### ROMとFlashの違い
- **ROM**: 電源を切っても消えないが、基本的に書き換え不可(または非常に限定的)。工場出荷時に焼き込まれたブートローダーの最初の一部などに使われる
- **Flash**: 電源を切っても消えないが、電気的に書き換え可能。ファームウェア本体はここに置かれる

## 命令セット(アーキテクチャ)

- Processor(CPU単体)かController(CPU+RAM+ROM+周辺回路のパッケージ)か、という設計の大分類(MCU/MPU)とは別軸で、「どの命令セットアーキテクチャを採用しているか」という軸がある
- 代表例: ARM(Cortex-M=MCU向け、Cortex-Aは MPU向け、という系統分岐がARM内にある)、RISC-V(MCU/MPU両方に使われる)、AVR(MCU専用、Arduino系)、Xtensa(MCU向け、ESP32)
- なぜ統一されないのか:
  - 後方互換性の呪縛(x86は1978年から続き、乗り換えコストが高い)
  - ライセンス/コストの問題(ARMは使用料が必要。RISC-Vはオープンソースで無料のため近年急速に普及)
  - 用途特化の最適化(超低消費電力向けと超高性能向けは原理的にトレードオフが相反する)
  - 企業の独自技術戦略(差別化・特許)

### なぜGhidraの前にアーキテクチャ特定が必要か
- ファームウェアのバイナリは0/1の機械語で、その解釈ルールはCPUアーキテクチャごとに全く異なる
- Ghidraは対象がどのアーキテクチャの機械語かを指定して初めて正しく逆アセンブルできる。間違えると意味不明な命令列になり解析が成立しない
- 実務の流れ: 基板上のチップ型番を確認 → データシートでアーキテクチャを特定 → Ghidraに設定 → 逆アセンブル

## 通信インターフェース: UART/SPI/I2C/JTAG

これらは「部品」ではなく、基板上のピン/パッドと、チップ内部のコントローラ回路を介した**通信規格(プロトコル)**。シリアル通信(1本の線で1ビットずつ順に送る方式。パラレル通信より高速化に強く現代の主流)の一種。

「繋いで何が得られるか」がインターフェースごとに全く違う:

| インターフェース | 主な用途 | 得られるもの |
|---|---|---|
| **UART** | シンプルな2線シリアル通信 | シェル/ターミナル(デバッグコンソール)。ただし認証があれば突破が必要。ログのみのことも多い |
| **SPI** | 高速なチップ間通信、Flashとの通信 | Flash内のfirmware dump(ファイルの塊)を直接読み出せる |
| **I2C** | 低速・多数のチップを1本のバスで共有(センサー間通信) | 個別チップ(EEPROM等)の設定データ・キー |
| **JTAG** | CPUのデバッグ・書き込み専用 | メモリ全体への直接アクセス+実行制御(最も強力。ソフトウェア的な認証を素通りできる) |

なぜこんなに種類があるか: 配線数を減らしたい(UART)/速度と大容量転送が欲しい(SPI)/多数デバイスを安く繋ぎたい(I2C)/ソフトウェアが動いていない状態でもハードウェアレベルで制御したい(JTAG)、という異なる要求に最適化された結果。命令セットが複数存在する構造と同じ。

## ブートプロセスの概念

電源投入から実際にOS/アプリが動き出すまでの段階的な起動の連鎖。

```
1. Boot ROM(CPU内蔵、書き換え不可)が起動
2. ブートローダー(例: U-Boot)が起動 → Flash上のカーネルを探して読み込み・実行
3. Linuxカーネルが起動 → ハードウェア初期化、ファイルシステムをマウント
4. アプリケーション/サービスが起動
```

MCU(RTOS)の場合はもっと単純で、ブートローダーがファームウェア全体を読み込んで即実行、という2〜3段階で終わることが多い。

### firmware dump とブートプロセスの関係(混同しやすい点)
- **firmware dump**: Flashチップの中身を丸ごとコピーした**静的なファイル**(ブートローダー・カーネル・ファイルシステムが1本のバイナリにまとまっている)
- **ブートプロセス**: そのFlashの中身を実行時に順番に読み込んで実行していく**動作**そのもの
- binwalkは、静的なdumpファイルを見て「どこからどこまでがブートローダー部分か」を切り分ける作業を行う

### なぜブートプロセスの理解が重要か(実務上の理由)
1. **firmware dumpの切り分けに必要**: binwalkで展開した各バイナリが、ブートプロセスのどの段階に対応するか分からないと、識別も解析方針の選択もできない
2. **エミュレーション(FSTMステップ6)の成否を左右する**: ブートローダーから起動させるかカーネルだけ抜き出すかで手法が変わり、構造を知らないとデバッグもできない
3. **攻撃計画の分岐点になる**: Secure Boot(各段階で署名検証を行うChain of Trustの仕組み)の有無で難易度が激変する
   - Secure Bootが**ない** → JTAG/UARTで改ざんファームウェアを書き込めばそのまま起動する(攻撃が単純)
   - Secure Bootが**ある** → ブートローダーの書き換えは弾かれ、検証ロジック自体のバグを探すか物理的直接読み出しに切り替える必要がある
   - これはOWASP I4(Lack of Secure Update Mechanism)/I9(Insecure Software/Firmware)に直結する
