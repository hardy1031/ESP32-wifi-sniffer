# Wi-Fi Sniffer プロジェクトで学ぶべき key takeaway

_Created: 2026-11-05_

このプロジェクト（特に reading break で着手する Phase 1）で何を持ち帰るか。優先順は、機器メーカー就職という目的から逆算したもの。

## 背景にある目的

- まず機器メーカーの「製品を動かす」「新機能を足す」枠に入り、機器の中身を学ぶ。
- このプロジェクトは研究の合間ではなく、就活の本体として取り組む（実機を触った経験が本命のアピール）。
- Phase 1 の「作る」側が、機器メーカーの開発職に一番近い。

## 1. 「好きか・できるか」の感触（最優先）

計画ファイル（`../../0825/20260825.md`）自身が一番の目的と書いている。reading break では Phase 1 の入口までしか進まないので、スキル習得より観察が本命。

- データシートや ESP-IDF の API ドキュメントを読む時間、flash して動かない時間に、苦痛か夢中か。
- 詰まったときに自分で前へ進めるか。
- ここが embedded を続けるかの判断材料になる。

## 2. 低レイヤーの C と、組み込みのデバッグの流れ（スキルの本命）

機器メーカーの開発職に転移するのはこれ。求人が共通して求める「C での開発」「実機でのデバッグ」そのもの（Fortinet の kernel/driver デバッグの縮小版）。

- ESP-IDF でビルドして flash し、動かないときにシリアルログやエラーから原因を追う。
- `wifi_promiscuous_pkt_t` のような構造体を、ポインタとビット演算で解釈する。
- 「PC の上のアプリ開発では触れない、ドライバに近い層を触った」という経験そのもの（`Sep14.md` の abstract の狙い）。
- resume や面接で話せるのは 802.11 の知識ではなく「このバグにこう詰まって、こう切り分けた」という話。

## 3. 802.11 と PCAP の中身の理解（副次）

フレーム構造や PCAP フォーマットは手を動かすが、これ自体は目的にしない。手段であって、暗記しても機器メーカーへのアピールにはなりにくい。

## まとめ

reading break で持ち帰るべきは「embedded のデバッグを一通り体験して、好きかどうかの答えを出すこと」。スキルとしては低レイヤー C とデバッグ、知識（802.11/PCAP）はそのついで。
